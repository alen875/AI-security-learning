# B01 东门子工业设备维护 Web 靶场实验指导手册

**修订日期：**2026-11-07。**适用源码：**`B01-2026.11.07-v5`，仓库提交 `b027a9e` 及其仅修改文档的后续提交。本手册覆盖环境、登录与业务、三个安全训练点、前端、审计、重置和验收，共 **55 个检查点**。下文是操作步骤和预期结果；实际结果须由实验者在批准环境中填写，不能用本手册代替实测证据。

## 本版实验内容与完成顺序

| 训练点 | 教学状态 | 固定入口 | 要验证的现象 | 安全状态的修复原则 |
|---|---|---|---|---|
| T1 对象级授权 | `idor` | `GET /api/records/{id}` | 已登录的维护员读取另一维护员的虚构记录 | 服务端核对记录归属 |
| T2 SQL 查询 | `sqli` | `GET /api/training-search?q=` | 教学布尔输入改变独立虚构索引的返回条数 | 参数绑定，输入仅作为数据 |
| T3 BP 报告预览 | `bp` | `POST /api/training/report-preview` | 普通维护员修改请求中的 `preview_role` 后读到受限虚构报告 | 以服务端会话角色判权 |

建议顺序是：先在 `safe` 模式完成环境和正常业务检查，保存数据摘要；再对 T1、T2、T3 **逐项**做安全状态与对应教学状态的同条件比较；每次切换都停服务、重新启动并重新登录；最后回到 `safe` 复测正常业务、核对审计和数据摘要。BP 是观察和修改 T3 请求的工具，T3 的根因是服务端错误信任客户端角色字段。本项目是自建教学模拟，不把公开漏洞公告当成原产品复现或厂商补丁验证。

已有的 22 项自动化测试已在本机通过，T3 的 HTTP 参数变化也做过本机对照；**Burp Suite 图形界面、Kali 与 Windows 虚拟机双机操作仍需在课堂现场执行**。下面的“预期”不是这些现场项目的完成证明。

## 一、实验准备与统一记录方法

### 1. 环境

先在 Windows 虚拟机的 PowerShell 中获取项目；仓库根目录含其他学习资料，本实验只使用 `dongmenzi-lab` 子目录：

```powershell
git clone https://github.com/alen875/AI-security-learning.git
cd AI-security-learning\dongmenzi-lab
py -3 --version
```

已经拉取过时，在 `AI-security-learning` 目录运行 `git pull`，然后进入 `dongmenzi-lab`。下列命令均以该子目录为当前目录。Git 和 Python 3.11 或更新版本须预先安装。

使用学校批准的隔离 Windows 虚拟机作为靶机；Kali 虚拟机只与该靶机所在的私有教学网络通信。禁止连接真实 ICS、PLC、SCADA、生产数据及公网。首次测试前保存虚拟机快照，确认教师许可、靶机私有地址、Windows 防火墙范围和版本号。所有测试只针对本项目预置虚构数据。

在 Windows 靶机的项目根目录安装并初始化：

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe init_db.py
.venv\Scripts\python.exe check_data.py
.venv\Scripts\python.exe run_range.py --mode safe
```

打开 `http://127.0.0.1:5000/`。在另一个 PowerShell 窗口进入同一目录，运行 `Invoke-RestMethod http://127.0.0.1:5000/healthz` 核对安全状态；`check_data.py` 应输出业务数据摘要。若 Python 启动器 `py` 不可用，用 `python -m venv .venv` 建虚拟环境。

切换教学状态时，先在服务窗口按 `Ctrl+C`，再按本次训练点选择**一个**命令；每次重新登录，并在页面与 `/api/lab/status` 确认模式：

```powershell
.venv\Scripts\python.exe run_range.py --mode idor
.venv\Scripts\python.exe run_range.py --mode sqli
.venv\Scripts\python.exe run_range.py --mode bp
.venv\Scripts\python.exe run_range.py --mode safe
```

上面四行是**四次分别启动的备选命令**，不要连续执行；当前服务停止后才能启动下一行。每个训练点先做 `safe` 对照，再做相应教学状态，最后回到 `safe` 复测。完成后在服务停止的情况下运行：

```powershell
.venv\Scripts\python.exe reset_sandbox.py --confirm RESET
.venv\Scripts\python.exe check_data.py
```

隔离虚拟机按教师批准流程离线导入依赖。初始化生成 `data/credentials.txt`，只在本机查看其中四个虚构账号的随机密码，不拍照或提交该文件。已有数据库时不要重复运行 `init_db.py`。改变状态时按 `Ctrl+C` 停止服务，再以 `--mode safe`、`idor`、`sqli` 或 `bp` 启动，每次只用一个模式。浏览器首页和 `/api/lab/status` 都应显示当前模式和构建号。

Kali 访问时，先核对两机处于获批私有网络；Windows 在明确批准后设置 `LAB_PRIVATE_NETWORK_APPROVED=yes` 并把 `--host` 指向 Windows 靶机的**具体私有 IP**。防火墙只允许 Kali 的私有 IP 访问选定端口。详细安装、网络和 API 说明见仓库根目录 `README.md`。

双机实验的可复制防火墙规则、限定来源地址的启动命令、Kali 健康检查以及规则清理命令均在 `README.md` 的“Windows 靶机与 Kali 双机测试”一节。只在本机运行时保持默认 `127.0.0.1`，不必运行该节的网络命令。

### 2. 预置对象与操作约定

| 身份 | 用途 | 预置数据 |
|---|---|---|
| `maint_a` | 维护员 A | 设备 101、201；记录 1、3 |
| `maint_b` | 维护员 B | 设备 102；记录 2 |
| `admin` | 培训管理员 | 可恢复业务基线、查看审计 |
| `reviewer` | 安全复核员 | 可查看审计及受限虚构报告，不能重置 |

“用 A 请求记录 2”表示以 `maint_a` 登录，然后在浏览器页面、开发者工具或 Burp Repeater 中向**自己的靶机**发出指定请求。HTTP 请求的 Cookie 取自该次登录；涉及 `POST` 的 T3、注销、重置还需保留 `/api/auth/me` 返回的本会话 `csrf`，放在 `X-CSRF-Token` 请求头。不得复用别人的会话或向其他地址发送请求。

每个测试填写：编号、日期时间、执行人课程编号、模式、构建号、种子版本、虚拟机网络摘要、账号角色、请求/操作、预期、实际、审计事件编号、截图或本地证据路径、结果（通过/失败/未执行）和限制。截图应遮盖凭据与会话 Cookie。业务数据前后摘要使用 `.venv\Scripts\python.exe check_data.py` 记录；审计事件增长不会改变 `business_digest`。

### 3. 先运行自动化检查

在项目根目录执行 `.venv\Scripts\python.exe -m unittest discover -s tests -v`，保存终端输出。自动化测试使用独立临时库，不代表双机网络和浏览器现场检查已通过。若某项失败，先按测试名定位，不继续演示对应脆弱状态。

| T2-03 | 不改变账号、输入、种子和请求方式，按 `sqli`→`safe` 再测；记录响应数量。 | 差异可重复；安全状态按参数绑定处理，普通查询仍正常。 |

## 六、T3 Burp Suite 请求参数篡改 T3-01–T3-05

使用 Kali 上的 Burp Suite 代理**自己的浏览器**，访问获批准的 Windows 靶机私有地址。T3 是独立训练点，状态为 `bp`。它使用 `POST` 传 JSON，但服务器只读取虚构报告、写审计，不修改业务数据。保持登录 Cookie 和 `X-CSRF-Token`，每次模式切换后重新登录。

| 编号 | 操作步骤 | 预期与证据 |
|---|---|---|
| T3-01 | A 在 `safe` 状态点击“预览普通维护报告”；在 Burp Proxy/HTTP history 找到 `POST /api/training/report-preview` 并送入 Repeater。 | 请求体为 `{"preview_role":"maint"}`；正常返回 `SIM-R01`。保存遮盖 Cookie/令牌的请求摘要。 |
| T3-02 | 在 Repeater 仅把该字段改为 `reviewer`，保留原会话与令牌；在 `safe` 发送一次。 | 返回 403，不包含 `SIM-R02` 的虚构受限摘要。 |
| T3-03 | 停服务，以 `bp` 模式启动；A 重新登录，再次执行 T3-01 和 T3-02。 | 普通请求仍返回 `SIM-R01`；改字段后返回 `SIM-R02`，表现为错误信任客户端角色参数。 |
| T3-04 | 切回 `safe`；用真实 `reviewer` 登录并预览 `reviewer` 报告；再用 A 重试。 | 复核员可正常读取，A 仍 403；说明修复保留合法业务。 |
| T3-05 | T3 前后各运行一次 `check_data.py`；查看审计；删除请求令牌重试一次。 | 业务摘要一致；审计记录预览及拒绝；缺令牌为 403。 |

BP 只是方便观察和修改请求的课堂工具；HTTP 客户端也能执行同样的参数变化，不能把“只能用 BP”写成漏洞特性。记录时说明这是自建虚构场景，不指称某个真实 CVE。

## 十一、结论填写页

对 T1、T2、T3 **分别**填写模板4（发生条件、实际现象、证据范围）和模板5（根因、修复、同条件复测、其他身份/输入/路径、正常业务回归）。只有实际发生失败时才填模板6。若某项网络、浏览器、负载或课堂条件没有执行，明确写“未执行/待验证”，不得把自动化测试结果扩展为全部现场测试通过。

最终结论从“可以交付 / 有条件可以交付 / 当前不建议交付”中选择一项，并写明教师许可、隔离范围、剩余风险、证据编号和会改变判断的条件。本手册中的“交付”只指批准隔离环境内的虚构教学演示，不构成真实工控系统部署许可。
