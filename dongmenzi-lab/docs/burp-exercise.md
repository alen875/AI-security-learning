# T3 Burp Suite 请求参数篡改练习

本训练点是原实验中的**第三个独立教学问题**，与 T1 的维护记录对象越权、T2 的 SQL 注入分开。业务情境为维护人员预览虚构培训报告；受限复核摘要仅应由复核员或管理员查看。脆弱状态错误地相信请求体中的 `preview_role`，修复状态以服务端会话中的真实角色作授权判断。

## 训练目标

学员应能说明：网页只显示普通按钮不能替代服务端授权；请求体中的角色字段可由客户端修改；修复应使用服务端已认证的角色，并验证普通业务仍可用。使用 Burp Suite 是课堂操作方式，HTTP 客户端同样能修改请求，因此不能声称“只有 BP 才能触发”。

## 环境与步骤

1. 在批准的隔离私网中启动 Windows 靶机，确认当前模式为 `safe`。Kali 浏览器通过 Burp Suite 代理访问靶机私有地址并以虚构维护员账号登录。
2. 打开页面中的“T3 BP 请求参数篡改”，点击“预览普通维护报告”。在 Burp 的 Proxy 或 Repeater 中找到 `POST /api/training/report-preview`。保留当前会话 Cookie 和 `X-CSRF-Token`，观察 JSON 请求体中的 `preview_role`。
3. 将该字段从 `maint` 改为 `reviewer`，仅向自己的教学靶机重放一次。`safe` 模式预计返回 `403`，不包含受限摘要；原普通请求仍返回 `SIM-R01`。
4. 停止服务，以 `bp` 模式重新启动同一靶场，核对状态接口和页面显示。使用相同虚构账号和同一字段变化重放。教学状态预计返回 `SIM-R02` 的虚构受限摘要。
5. 切回 `safe`，再次验证字段变化被拒绝、真实复核员可正常预览 `SIM-R02`，并核对审计事件及业务数据库内容摘要没有变化。

这是只读请求：`POST` 用于承载被拦截的 JSON 请求体，后端不对设备、维护记录或报告作写入。练习不涉及真实企业资料，也不允许将请求发往其他目标。

## 证据记录

分别记录 `safe` 与 `bp` 的构建号、启动时间、账号角色、靶机私有地址摘要、请求字段变化、HTTP 状态、响应摘要、审计事件、业务数据库前后摘要。实际结果必须由课堂运行填写；预期文字不能代替实测。若会话或令牌失效，重新登录再做同条件对照，不通过关闭令牌检查“解决”问题。
